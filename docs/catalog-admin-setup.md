# YOCARD 카드 DB와 관리자 페이지 연결

현재 구현은 다섯 카드의 검수용 초안이다. 사용자 페이지는 기존 카드 데이터 파일을 계속 사용한다. 관리자에서 검수 완료로 표시하거나 저장해도 사용자 서비스에 자동 배포되지 않는다.

## 지금 바로 확인

프로젝트 폴더에서 다음 명령으로 서버를 실행하고 관리자 페이지를 연다.

```text
node scripts/serve.js
```

주소: http://127.0.0.1:4173/admin.html

- 기본 화면은 미리보기다. 관리자 로그인 후 실제 DB의 카드 정보를 연다. 카드명·브랜드로 검색하면 기본 화면에서 전체 혜택과 조건을 읽을 수 있다.
- 적용 브랜드, 지급 방식·단위, 비율·정액·금액 구간·누적 적립, 전월 실적, 최소 결제금액, 결제 방식, 조건과 검수 메모를 수정할 수 있다.
- 카드 상단의 통합한도 표와 각 혜택의 개별 한도 옆에서 ‘수정’을 누른다. 실적 구간·함께 적용되는 통합한도·연결 혜택을 수정할 수 있다.
- 수정 창의 ‘변경사항 적용’ 후 상단의 ‘카드 저장’을 누른다. 미리보기에서 저장한 내용은 이 브라우저에만 보관된다.
- 내용이 맞으면 수정 창을 열지 않고 혜택의 ‘검수 완료’를 누른 뒤 카드 저장을 누른다. 혜택 수치를 바꾸면 검수 전으로 돌아간다.
- ‘기존 정리와 비교’는 원래 데이터의 표시 문구를 보여준다. 원문은 수정해도 유지된다.
- 공식 안내·카드고릴라 링크는 상단과 수정 창에 있으며 각각 새 탭으로 열린다. 외부 페이지를 삽입하지 않는다.
- 백업 파일 관리의 내보내기·가져오기로 파일을 보관할 수 있다. 가져오기는 로컬 초안을 저장하며 Supabase에 쓰지 않는다.

## Supabase에 실제 적용

원격 적용은 프로젝트 소유자 권한이 필요하다. 브라우저에 들어 있는 publishable key만으로 테이블을 만들거나 관리자 권한을 부여할 수 없다. secret/service_role 키를 웹 코드에 넣지 않는다.

1. YOCARD Supabase 프로젝트의 SQL Editor에서 `supabase/catalog-schema.sql`을 실행한다.
2. Authentication > Users에서 관리자용 이메일·비밀번호 계정을 만든다. 기존 계정을 운영자로 지정할 수도 있다. 일반 사용자의 설정 코드와는 별도이며, 관리자 페이지에는 회원가입 기능이 없다.
3. `supabase/catalog-admin.sql`의 이메일 한 곳을 실제 관리자 이메일로 바꾸고 SQL Editor에서 실행한다.
4. SQL Editor에서 `supabase/catalog-seed.sql`을 실행한다. 다섯 카드의 초안과 개별 적용 대상을 가져온다. 기존 카드 초안이 있으면 충돌 오류를 내고 전체 가져오기를 롤백하므로 수정한 카드를 덮어쓰지 않는다.
5. `admin.html`의 ‘관리자 로그인’을 눌러 지정한 계정으로 로그인한다. 연결되면 상단에 ‘DB 연결됨’이 표시된다.
6. 카드 초안을 수정하고 저장한 다음 다시 연결하여 보존 여부를 확인한다.

로컬 초안은 DB 연결 시 자동 업로드하지 않는다. 먼저 내보내기로 보관할 수 있다. DB 연결 후에는 DB에 저장된 초안을 읽어 편집한다. 로컬 브라우저 로그인은 별도의 저장 키를 사용해 기존 사용자 설정 코드 세션과 구분한다. 현재 자동 재연결은 제공하지 않으며 관리자 페이지에서 다시 연결한다.

## 저장 구조

| 테이블 | 역할 |
| --- | --- |
| yocard_catalog_admins | 운영자가 명시적으로 부여한 관리자 권한 |
| yocard_catalog_cards | 카드 기본 정보·검수 상태·출처·변경 버전·원본 스냅샷 |
| yocard_catalog_targets | 개별 브랜드·업종·서비스·전체 가맹점 대상 |
| yocard_catalog_benefits | 지급 방식·단위·계산 규칙·실적·결제 조건 |
| yocard_catalog_benefit_targets | 혜택과 개별 대상의 포함·제외 연결 |
| yocard_catalog_limits | 금액·횟수·이용금액 한도, 실적별 값, 상위 공유 한도 |
| yocard_catalog_limit_benefits | 한도를 함께 사용하는 혜택 연결 |
| yocard_catalog_relations | 추가·대체·중복 불가 관계 |
| yocard_catalog_sections | 카드정보창에서 함께 보여줄 묶음 |
| yocard_catalog_section_benefits | 표시 묶음과 계산 규칙 연결 |
| yocard_catalog_revisions | 저장자·시각·버전과 당시 카드 전체 스냅샷 |

브랜드가 나열된 문장을 매칭 대상으로 사용하지 않는다. 노리2 커피는 하나의 혜택에 스타벅스와 커피빈을 각각 연결하고, 두 브랜드가 같은 월 한도를 공유한다. 이름·출처·원래 표시 문구에는 사람이 읽을 문장이 들어갈 수 있다.

## 표본 변환

원본 63행을 56개 규칙으로 옮겼다. 우리 POINT의 합산값을 중복 저장하던 숨김 7행은 기본·특별 규칙과 간편결제 추가 3%의 관계로 연결한다. 63개 원본 ID는 `source_snapshot.mappings`에 모두 남아 있다. 원본 행 자체도 보존한다.

어학시험은 TOEIC·OPIc·TEPS·JPT·HSK를 각각 연결하며 철도·버스도 KTX·SRT·ITX·고속버스·시외버스의 서비스 범위를 각각 연결한다. 포인트 적립 한도는 포인트, 별 적립 한도는 별 단위를 사용하고 원화 한도와 섞지 않는다.

국민행복카드는 쇼핑·보육·생활요금 공유 한도 3개가 전체 통합한도에 연결된다. 나라사랑 PX는 3만원 미만과 이상 구간을 구분하며, 스타벅스 현대카드는 별 단위·누적 3만원·잔여 이월을 원래 단위로 기록한다. 원본에 없는 수치는 임의로 무제한·조건 없음으로 확정하지 않고 미확인으로 남긴다.

이번 변환은 기존 정리의 구조화다. 공식 약관을 다시 검증하거나 기존 사용자 추천의 오류를 수정한 결과는 아니다. 관리자에서 원문과 함께 검수하도록 한다.

## 검수 단계의 범위

현재는 기존 규칙의 조회·비교·수정이 중심이다. 새 카드·브랜드·혜택 생성, 신규 한도 생성, 표시 묶음·혜택 관계 자체 편집, 과거 버전 복원, 검수된 데이터의 사용자 페이지 게시 기능은 아직 제공하지 않는다. 원격 DB 연결과 실제 계정 인증은 위 소유자 설정을 완료한 후 확인해야 한다.

현재 모델은 계산 유형이 정해진 버전 1 규칙만 받는다. 복잡한 조건의 원문은 보존하며 새 유형으로 승인되지 않은 문장을 자동 계산하지 않는다. 다섯 카드에 필요한 입력 화면을 검수한 뒤 남은 카드와 규칙 유형을 확장한다.

## 검증

```text
node scripts/build-catalog-seed.js
node scripts/test-catalog.js
node scripts/validate-data.js
```

SQL 테스트는 [PGlite의 PostgreSQL 엔진](https://pglite.dev/docs/)에서 실행한다. 개발 환경에서 `npm install` 후 다음 명령을 사용한다.

```text
node scripts/test-catalog-db.mjs
```

npm이 없는 작업 환경에서는 선택적으로 `node scripts/fetch-test-runtime.js`를 사용할 수 있다. 공식 레지스트리에서 package.json에 고정한 PGlite 버전만 무결성 검사 후 `.catalog-test-deps`에 내려받는다. 이 폴더는 Git에서 제외한다.

검증 범위는 스키마 재실행, 표본 가져오기, FK, 관리자·일반 사용자·비로그인 권한, 권한 자가 부여 차단, 원자 저장·실패 롤백, 동시 편집 충돌, 원본 보존, 변경 이력, 기존 `user_settings` 보존이다.

브라우저 검증은 미리보기 서버를 켠 상태에서 `npm run test:ui`를 실행한다. 기본 브라우저는 headless Microsoft Edge다. `PLAYWRIGHT_MODULE`과 `TEST_BROWSER_CHANNEL` 환경변수로 이미 설치된 테스트 도구와 브라우저를 지정할 수 있다. 원격 어댑터 테스트는 모의 응답으로 연결·저장·충돌 시 초안 보존을 검증하며, 실제 Supabase 로그인을 대신 검증한 것은 아니다.

서버 권한 설정은 [Supabase RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)와 [DB 함수 안내](https://supabase.com/docs/guides/database/functions)의 권한·search_path 원칙을 따른다. 관리자 이름을 프런트엔드에서 검사하는 방식 대신 DB에서 권한을 검사하고, 쓰기는 검증과 이력 저장을 한 트랜잭션으로 수행하는 함수만 허용한다.
